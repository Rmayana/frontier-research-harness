# 수련 연구 에이전트 기능 설계

버전: 0.1 · 기준일: 2026-11-01 (Asia/Seoul)
상태: 대화에서 논의한 기능을 정리한 아키텍처 설계용 기준안.
근거: [요구사항 명세](SPECIFICATION.md), 요구 내용 기준 v0.16.

## 1. 문서의 역할과 설계 원칙

이 문서는 요구사항을 만족하려면 어떤 기능이 필요하며 어떻게 동작해야 하는지 정의한다.
기능별 동작 흐름·결과·확인 방법과 연결을 다룬다. 모듈·API·저장 기술·플러그인 배치는
아키텍처 및 상세 기술 설계에서 결정한다. 각 기능을 별도 모듈이나 에이전트로 만든다는 뜻은 아니다.

- 사용자가 기능 설계의 문서화를 요청한 시점의 기준안이다. 세부 흐름과 확인 방법은 설계 제안이며 검토하며 보완한다.
- 요구의 확정·보류 여부는 명세가 기준이다. 이 문서가 미정 요구를 자동 확정하거나 실제 수련·개인 실험을 승인하지 않는다.
- 기능은 판단 → 행동 → 결과 확인 → 다음 대응이 드러나도록 설명한다. 모든 연구에 동일 순서·횟수·도구를 강제하는 상태 기계는 아니다.
- 한 중심 문제의 관련 작업은 병렬로 조사할 수 있다. 중심 문제와 큰 방향의 변경은 사용자와 논의한다.
- 문헌 검토의 양과 깊이를 모두 확보한다. 인용 수·에이전트 수·계산량만으로 연구 품질을 판단하지 않는다.
- 실행 성공, 결과의 유용성, 과학적 타당성, 개인 적용 적합성을 구분한다.
- 기본 기능으로 제공되는 능력도 기능 설계에 포함한다. 추가 구현 여부는 실제 실행 환경을 확인해 정한다.

## 3. 기능별 동작

### F01. 목표 분석·구체화

- 요구 근거: 명세 §1·2·3·9. 사용자가 세부 지표를 미리 준비하지 않아도 목표를 연구 가능한 형태로 발전시킨다.
- 흐름: 장기 방향과 현재 목표를 확인한다 → 목표 선수·관련 자료를 조사한다 → 필요한 능력과 관계를 도출한다 → 개인 상태와 비교한다 → 목표·확인 방법·잠정 우선순위를 제안해 함께 정한다.
- 결과: 현재 목표, 관측할 능력과 기준 후보, 알려진 차이와 미확인 부분.
- 확인: 베테르비에프의 모습에서 확인되지 않는 내부 상태를 사실로 채우지 않고, 더 유리한 목표 방향이 나오면 변경 이유를 제안한다.

### F02. 개인 상태·환경 파악

- 요구 근거: 명세 §5·6·9. 실제 몸과 생활 여건에 맞는 판단이 필요하다.
- 흐름: 알려진 기록을 확인한다 → 현재 판단에 부족한 정보를 찾는다 → 필요한 질문을 묶어 묻는다 → 답변과 자료의 시점·조건을 확인한다 → 상태와 환경을 갱신한다.
- 결과: 현재 파악한 능력·경험·상태·일정·시설과 미확인 사항.
- 확인: 이미 알려준 내용을 불필요하게 반복해서 묻지 않고, 기록 공백을 미수행으로 해석하지 않는다. 사용자가 돌아왔을 때 변화 여부를 확인한다.

### F03. 전체 설명·발전 방향 갱신

- 요구 근거: 명세 §3·5·9. 개별 조사를 전체 목표에 연결한다.
- 흐름: 목표·개인 상태·연구 결과를 모은다 → 능력 간 관계와 가능한 제한 요인을 설명한다 → 모순과 공백을 찾는다 → 전체 설명과 잠정 발전 방향을 개정한다 → 영향을 받는 연구·모델·수련안을 표시한다.
- 결과: 현재 전체 설명, 근거·가설·미확인의 구분, 변경 이유와 후속 검토 대상.
- 확인: 특정 현상의 가설(F06), 개인 예측 모델(F10), 전체 발전 방향을 혼동하지 않고 새 결과가 큰 그림에 어떻게 영향을 주는지 설명한다.

### F04. 연구 질문 생성·다음 행동 선택

- 요구 근거: 명세 §3·4. 지능적 연구와 연쇄적인 질문을 수행한다.
- 흐름: 현재 목표·설명·작업 결과를 확인한다 → 중요한 문제와 후속 질문을 만든다 → 어떤 결과가 판단을 바꿀지 검토한다 → 조사·분석·계산·관측 제안 중 다음 행동을 선택한다 → 결과에 따라 계속·변경·질문·보류를 판단한다.
- 결과: 선택한 질문·행동·이유, 후속 질문과 보류 이유.
- 확인: 최초 질문 자체의 오류 가능성을 검토하고, 사용자가 답하지 않아도 합의 범위 안의 유용한 작업은 계속한다. 고정 질문 점수나 필수 단계로 대신하지 않는다.

### F05. 폭넓은 자료 탐색·심층 검토

- 요구 근거: 명세 §3. AI의 정보 처리·병렬 조사 능력을 활용해 많은 자료를 깊이 검토한다.
- 흐름: 관련 분야·검색 관점을 도출한다 → 공개 문헌·원자료·영상·방법 자료를 폭넓게 찾는다 → 관련성과 출처를 확인한다 → 중요한 원문을 검토한다 → 인용·상충 결과·인접 분야를 따라 확장한다 → 공통점·차이·연결·남은 공백을 종합한다.
- 결과: 검토한 근거와 출처, 자료 간 관계, 상충 결과, 추가 조사 후보.
- 확인: 발견·선별·실제 내용 검토를 구분한다. 같은 근거의 재인용을 독립 증거처럼 세지 않는다. 접근하지 못한 내용은 확인한 근거로 사용하지 않는다.
- 범위: 공개 자료 우선, 기존 자원 한도 유지. 유료 자료가 필요하면 공동 결정한다.

### F06. 과학적 설명·경쟁 가설 검토

- 요구 근거: 명세 §1·3. 실제 과학 원리 안에서 현상의 이유를 연구한다.
- 흐름: 관찰 사실과 해석을 구분한다 → 가능한 기전·대안 설명을 만든다 → 전제·지지 근거·반례를 비교한다 → 설명을 구별할 조사나 관측을 제안한다 → 결과에 따라 설명을 수정하거나 미확인으로 남긴다.
- 결과: 근거와 조건이 연결된 설명·경쟁 가설·불확실성·추가 확인 방법.
- 확인: 관찰된 상관을 인과로 단정하지 않는다. 약한 근거와 반례가 다음 판단에 실제로 영향을 준다. 과학적 판단 근거와 중요한 검토 결과를 설명한다.

### F07. 계산·시뮬레이션과 결과 검토

- 요구 근거: 명세 §3·5·7. 정량적 비교와 가정에 따른 예측을 지원한다.
- 흐름: 계산이 필요한 질문을 정한다 → 모델·입력·가정을 확인한다 → 실행한다 → 오류·단위·조건과 결과를 검토한다 → 주요 조건을 바꾸어 결론의 민감도를 확인한다 → 관측과 비교하거나 검증 공백을 밝힌다.
- 결과: 재확인 가능한 입력·방법·출력, 가정과 적용 범위, 예측의 불확실성.
- 확인: 계산 실행 성공을 현실의 효과·안전 입증으로 취급하지 않는다. 정량화 근거가 없으면 정확한 수치를 만들어내지 않는다.

### F08. 선수의 수행·훈련 역설계

- 요구 근거: 명세 §2·3. 신체와 무공을 가능한 한 자세히 분석한다.
- 흐름: 경기·훈련 자료를 확보한다 → 실제 관찰되는 동작·조건을 분석한다 → 신체 능력·협응·감각·판단과 연결한다 → 훈련 의도와 적응 기전을 가설로 설명한다 → 관련 근거와 다른 사례로 검토한다 → 개인에게 적용할 원리와 차이를 도출한다.
- 결과: 수행을 설명하는 후보 기전, 훈련 목적의 추정, 개인 적용·개선 후보.
- 확인: 영상에서 관찰한 세트·반복, 추정한 훈련 의도, 새로 설계한 개인 훈련량을 명확히 구분한다. 한 사례의 관찰을 전체 루틴으로 일반화하지 않는다.

### F09. 공법 후보 개발·비교

- 요구 근거: 명세 §3. 기존 방법 개선과 원리에 기반한 새로운 방법 개발은 모두 기본 역할이다.
- 흐름: 목표 능력과 관련 원리를 확인한다 → 기존 방법을 분석한다 → 조합·개선·새 방법 후보를 만든다 → 근거·계산·조건을 검토한다 → 이득·손실·불확실성을 비교한다 → 추가 연구 또는 적용 검토를 제안한다.
- 결과: 방법 후보, 작동 원리, 예상 효과·실패 조건, 비교와 검증 방법.
- 확인: 매번 새 발견을 보장하지 않는다. 능력 간 이득·손실은 사용자와 함께 판단하며 기존 방법보다 우수하다는 주장은 검증 수준에 맞춘다.

### F10. 개인 모델 형성·보정

- 요구 근거: 명세 §5·10. 사용자 개인의 반응과 변화에 대한 설명·예측을 발전시킨다.
- 흐름: 현재 문제에 필요한 관계를 정한다 → 개인 관측과 관련 근거로 설명·모델을 만든다 → 방법별 결과를 예측한다 → 실제 결과와 비교한다 → 조건·개인차·모델 오류를 검토한다 → 모델을 수정하거나 유지 이유를 기록한다.
- 결과: 개인별 설명과 예측, 검증 범위, 수정 이력.
- 확인: 데이터가 적을 때 일반 근거와 개인에게 확인된 관계를 구분한다. 전신 모델은 검증하며 확장하는 장기 방향이며 첫 버전에 완성하지 않는다.

### F11. 구체적인 수련안 제안·조정

- 요구 근거: 명세 §6·9. 연구를 실제 일상 수련과 연결한다.
- 흐름: 필요한 초기 상태·환경을 파악한다 → 현재 근거로 잠정안을 만든다 → 당일 시간·상태·시설을 반영한다 → 내용·분량·빈도·관찰할 점과 원리를 설명한다 → 수행 결과와 변동을 받아 다음 안을 조정한다.
- 결과: 사용자가 검토·수행할 수 있는 구체적인 수련안과 이유·예측.
- 확인: 새 공법이나 개인 모델 완성을 기다리지 않고 현재 근거로 잠정안을 제안한다. 학교·군대의 고정 조건을 지킨다. 불확실한 개인 적용은 F14와 연결한다.

### F12. 수행 기록·영상·측정 수집

- 요구 근거: 명세 §6. 짧고 지속 가능한 기록과 가치 있는 추가 관측이 필요하다.
- 흐름: 사용자가 기록을 요청하거나 수행 정보를 전한다 → 기존 계획·정보를 확인한다 → 필요한 질문만 묶어 제시한다 → 사실·계획·추정을 구분해 기록한다 → 저장 내용을 알린다 → 영상·추가 측정이 판단에 크게 도움 될 때 이유와 방법을 제안한다.
- 결과: 시점·조건·누락이 드러나는 수행·상태 기록과 필요한 추가 관측 제안.
- 확인: 답하지 않은 값을 채우지 않는다. 기록 없는 날에 먼저 상태 확인 연락을 하지 않고, 돌아왔을 때 확인한다. 실제 촬영·측정 조건과 부담은 함께 정한다.

### F13. 실제 결과 평가·연구 피드백

- 요구 근거: 명세 §3·5·9. 실제 데이터가 설명과 수련에 영향을 주어야 한다.
- 흐름: 예측과 실제 관측을 연결한다 → 측정·수행 조건을 확인한다 → 변화와 불일치를 분석한다 → 가능한 원인을 조사한다 → 공법·개인 모델·다음 수련·연구 질문의 재검토를 제안한다.
- 결과: 무엇이 지지·반박·미확인인지, 수정하거나 유지할 이유와 다음 확인 사항.
- 확인: 기록 변화만으로 효과나 인과를 확정하지 않는다. 수정된 설명에 의존하던 다른 결과도 재검토 대상으로 연결한다.

### F14. 개인 적용 검토

- 요구 근거: 명세 §7·11. 새로운 방법의 연구 결과와 실제 개인 적용을 구분한다.
- 흐름: 후보 방법의 근거·적용 조건을 확인한다 → 개인 상태·환경과 대조한다 → 남은 불확실성·위험·예상 이득을 설명한다 → 필요한 평가·중단·추적 관찰 조건을 제안한다 → 사용자와 적용 여부 및 추가 검토를 정한다.
- 결과: 적용 판단에 필요한 정보, 미해결 조건, 합의한 경우의 관측 계획.
- 확인: 시뮬레이션이나 짧은 무증상 관측을 장기 안전 확증으로 취급하지 않는다. 구체적 개입의 허용 범위는 미정이며 이 문서가 실행 승인이 아니다.

### F15. 공동 해석·결정·지시·위임 반영

- 요구 근거: 명세 §4. 사용자는 정보 제공뿐 아니라 해석과 방향 결정에도 참여한다.
- 흐름: 해석·아이디어·선택이 필요한 지점을 찾는다 → 근거와 대안을 설명해 질문한다 → 사용자 의견과 기존 합의의 관계를 확인한다 → 방향·작업·위임 범위를 갱신한다 → 달라진 내용을 알린다.
- 결과: 선택·이유·위임 범위와 변경 이력, 필요한 후속 행동.
- 확인: 초기에는 방향·접근을 함께 정한다. 합의 범위 내 세부 작업마다 재승인을 요구하지 않는다. 위임 확대·변경은 합의하고, 답변 대기 중 진행 가능한 기존 범위 작업은 계속한다.

### F16. 의미 있는 결과 보고·근거 확인

- 요구 근거: 명세 §3·4·5. 원리·근거·예측을 이해하고 의견을 줄 수 있어야 한다.
- 흐름: 의미 있는 결과나 판단 변화를 확인한다 → 관련된 작은 발견을 모은다 → 원리·근거·예측·불확실성과 달라진 판단을 설명한다 → 원자료·계산·검토 기록을 연결한다 → 사용자 질문·수정을 반영한다.
- 결과: 읽기 쉬운 보고와 상세 근거로의 접근.
- 확인: 모든 도구 이벤트를 보고하는 방식으로 대체하지 않는다. 연구 결과와 실행 오류, 추정과 확인 사실을 구분한다. 표시 가능한 판단 근거를 설명하며 내부 추론 전문 공개를 요구하지 않는다.

### F17. 장기 기억·원본 보존·검색

- 요구 근거: 명세 §4·6·9·10. 저장을 넘어 나중 판단에서 활용해야 한다.
- 흐름: 연구·관측·합의·실패와 원본을 보존한다 → 출처·시점·조건·관계를 연결한다 → 관련 작업에서 검색한다 → 현재 유효성과 변경 이력을 확인한다 → 활용한 내용과 수정 사항을 반영한다.
- 결과: 다시 찾을 수 있는 원본·근거·관측·결정·설명 이력.
- 확인: 세션이 바뀌어도 이전 합의와 근거를 찾아 활용한다. 수정 전 내용을 현재 사실로 혼동하지 않는다. 새 출처와 원본으로 돌아갈 수 있다.
- 범위: 우선 원본을 보존한다. 공간 부족 시 선별 기준·삭제 권한·정정 방식은 미정이며 임의 삭제하지 않는다. 공개 저장소와 개인 자료는 F27에서 구분한다.

### F18. 작업 문맥 구성·갱신

- 요구 근거: 명세 §10. 지금 판단에 필요한 내용을 사용할 수 있어야 한다.
- 흐름: 현재 문제와 작업을 확인한다 → 목표·관련 기억·근거·합의·진행 상태를 찾는다 → 중요 조건과 미해결 모순을 보존해 제공한다 → 정보 공백이나 문제 변경이 생기면 원자료를 찾아 보충·갱신한다.
- 결과: 현재 작업과 위임할 작업에 필요한 문맥.
- 확인: 많은 자료를 모두 동시에 넣는 것을 전제하지 않는다. 요약에서 빠진 조건을 원본으로 확인할 수 있고, 이전 목표·추측이 최신 합의를 대체하지 않는다.

### F19. 도구 탐색·자동 선택·실행 결과 확인

- 요구 근거: 명세 §3·10. 사용자가 도구 호출을 하나씩 지시하지 않아도 된다.
- 흐름: 필요한 정보와 작업을 판단한다 → 사용 가능한 도구·입출력·제약·권한을 확인한다 → 도구를 선택해 실행한다 → 정상 실행 여부와 결과가 질문에 답하는지 확인한다 → 부족하거나 실패하면 대체 방법·추가 도구 필요를 판단한다.
- 결과: 검토한 도구 결과와 선택·대응의 중요한 이유.
- 확인: 실행 성공을 연구 성공으로 간주하지 않는다. 새로운 비용·권한·개인 자료 외부 제공은 기존 합의에 따른다. 필요한 도구가 없으면 F24와 연결한다.

### F20. 작업 분해·진행 관리

- 요구 근거: 명세 §3·8·10. 장기·병렬 작업의 누락과 반복을 줄인다.
- 흐름: 현재 문제를 필요한 작업으로 나눈다 → 의존 관계와 공유 결과를 파악한다 → 진행·대기·실패·완료를 갱신한다 → 중복·누락·정체를 점검한다 → 새로운 결과에 따라 작업을 추가·수정·취소한다.
- 결과: 현재 작업 상태, 막힌 이유, 다음 실행 가능한 작업.
- 확인: 자료 대기 작업과 실행 가능한 작업을 구분한다. 일의 완료와 과학적 결론의 타당성을 구분하고, 같은 실패를 이유 없이 반복하지 않는다.

### F21. 서브에이전트 생성·조정·통합

- 요구 근거: 명세 §3·10. 다양한 관점·조사량·독립 검토를 활용한다.
- 흐름: 분담과 독립 검토의 필요성을 판단한다 → 임무·범위·관련 문맥·기대 결과를 전달한다 → 중간 질문·발견을 교환한다 → 중복·실패·상충 결과에 대응한다 → 메인이 근거와 결과를 통합한다 → 필요하면 추가 조사·재배정·종료한다.
- 결과: 근거·조건·불확실성이 포함된 조사 결과와 통합 설명.
- 확인: 임무는 문제에 맞춰 동적으로 정한다. 에이전트 간 의견 일치를 독립된 과학적 증거로 세지 않는다. 주요 설명과 전략은 메인이 개정하고 자원 한도를 유지한다.

### F22. 오류 대응·실행 복구

- 요구 근거: 명세 §8·10. 도구·작업 실패 뒤에도 실제 상태를 파악하고 대응한다.
- 흐름: 실행 오류나 이상을 감지한다 → 원인과 완료 여부·영향을 확인한다 → 재시도·대체 방법·질문·보류 중 대응을 선택한다 → 복구 결과를 확인한다 → 실패와 대응을 기억한다.
- 결과: 복구한 작업 또는 명확한 실패·보류 사유와 다음 선택.
- 확인: 실행 여부가 불명확한 작업을 무조건 재실행하지 않는다. 접근 실패를 근거 없음으로 해석하지 않는다. 복구 불가능할 때 완료했다고 보고하지 않는다.

### F23. 중단·재개·자원 관리

- 요구 근거: 명세 §8·9·10. Codex 구독과 중단 원칙 안에서 지속한다.
- 흐름: 확인 가능한 사용량·실행 상태를 살핀다 → 한도·정지 요청에 대응한다 → 일반 정지는 새 작업을 막고 가능한 정리를 수행하며 즉시 중단은 진행 계산 중지도 시도한다 → 결과·미해결 사항·작업 상태·다음 행동·중단 이유를 보존한다 → 사용자 재개 지시 후 상태를 확인해 이어간다.
- 결과: 중단·재개 상태와 보존한 연구 맥락, 복구되지 않은 작업의 표시.
- 확인: 사용량 회복 뒤 자동 재개하거나 별도 유료 API로 전환하지 않는다. 확보된 정보로만 회복 예정 시각을 안내한다. 실제 한도 감지·사전 정리·중단 가능 범위는 호스트에서 검증한다.
- 범위: 초기에는 회복 여부를 사용자가 확인한다. PC 종료 중 실행과 무기한 상시 실행은 같은 요구가 아니다.

### F24. 연구 도구·작업법 확장

- 요구 근거: 명세 §3. 부족한 분석 능력을 정한 범위 안에서 발전시킨다.
- 흐름: 필요한 능력과 기존 도구의 공백을 확인한다 → 기존 도구 연결과 코드 개발을 비교한다 → 합의한 자원·권한 안에서 구현·설정한다 → 실제 예시와 오류 조건으로 검증한다 → 결과와 한계를 보고하고 유용한 방법을 재사용한다.
- 결과: 검증 범위를 명시한 도구·분석 코드·재사용 가능한 작업법.
- 확인: 설치·코드 생성만으로 유효성을 인정하지 않는다. 추가 비용·권한은 공동 결정한다. 하네스 전반의 자동 변경 승인으로 확대하지 않는다.

### F25. 하네스 개선 제안·평가

- 요구 근거: 명세 §3. 모델 가중치가 아닌 연구 지원 체계를 경험으로 개선한다.
- 흐름: 연구 과정·결과를 살핀다 → 반복되는 누락·실패·비효율·부족한 능력을 찾는다 → 원인과 개선 가설을 만든다 → 지침·스킬·도구·기억·분업·실행 코드·플러그인 변경 또는 기능 추가를 제안한다 → 함께 검토한다 → 채택·구현된 변경의 효과를 확인해 다음 제안에 반영한다.
- 결과: 문제 근거, 변경안, 예상 효과·비용·불확실성, 비교·검증 방법.
- 확인: 스스로 수정·배포하는 기능은 필수가 아니다. 변경 사실을 개선의 증거로 대신하지 않는다. 반영 절차와 평가 기준은 후속 설계에서 구체화한다.

### F26. 모바일 대화·연구 이용

- 요구 근거: 명세 §8. 기존 Codex 구독으로 모바일에서 이용한다.
- 흐름 초안: 모바일에서 연구 대화에 접근한다 → 방향 논의·기록·결과 확인·연구 제어를 수행한다 → 실제 실행 상태와 결과를 확인한다 → 끊긴 경우 상태를 확인하고 이어간다.
- 결과: 모바일에서 이어지는 연구·수련 이용 경험.
- 확인: 공식 ChatGPT 앱을 우선한다. 모바일에서 지원할 정확한 작업 범위와 기기, 실행 호스트의 연결·중단 조건은 검증·합의가 필요하다.
- 후보 순서: Codex Cloud + 플러그인 → 개인 PC 없이 이용 가능한 대안 → PC를 켜 둔 원격 이용. 앞선 후보가 부족하면 근거와 절충을 설명하고 함께 다음 구성을 선택한다.

### F27. 개인 자료·외부 제공 관리

- 요구 근거: 명세 §6·8 및 저장소 운영 원칙. 개인 자료의 공개·제공 범위를 관리한다.
- 흐름: 다룰 자료와 저장·전송 목적지를 확인한다 → 개인 자료인지와 기존 합의 범위를 확인한다 → 새로운 외부 분석 서비스 제공이면 자료·목적·서비스를 설명한다 → 합의한 범위에서 처리하고 기록한다.
- 결과: 공개 자료와 구분된 개인 자료, 외부 제공에 관한 결정과 처리 기록.
- 확인: 공개 GitHub 저장소에 개인 영상·몸 상태·측정값·비밀정보를 올리지 않는다. 공개 선수 자료 조사는 기존 범위에서 자율 수행한다.

## 4. 기능 연결과 책임의 구분

대표 사용 흐름은 다음과 같다. 여러 갈래로 돌아가거나 병렬 수행할 수 있다.

목표·개인 이해(F01–03) → 문제·접근 합의(F04·15) → 자료·가설·계산·역설계(F05–08)
→ 공법·개인 예측(F09–10) → 적용 검토·수련안(F14·11) → 기록·관측(F12)
→ 실제 결과 평가(F13) → 전체 설명·모델·다음 연구·수련 갱신.

- 연구 진행 중에도 현재 근거로 잠정 수련안을 제안한다. 모든 연구가 끝날 때까지 기다리는 흐름이 아니다.
- F04는 다음 연구의 내용과 이유를 판단한다. F20은 작업 상태·의존 관계·누락을 관리한다.
- F17은 지속 보존과 검색을, F18은 지금 작업에 필요한 문맥 구성을 담당한다.
- F19는 도구 선택·실행 결과 확인을, F22는 실패의 영향 파악과 복구 대응을 담당한다.
- F21은 분담과 통합을 지원한다. 분담 자체가 연구 품질을 보장하지 않는다.
- F15·16은 전 과정의 공동 판단과 보고에 연결된다. F23·27의 자원·개인 자료 조건도 전 과정에 적용한다.
- F24는 합의 범위 안의 연구 도구 확장이다. F25는 하네스 개선 제안이며 자동 수정 의무가 아니다.

## 5. 첫 버전과 확장 범위

### 첫 버전에서 실제로 연결할 범위

목표·문제·접근 합의, 실제 자료와 분석을 활용한 연구, 근거·원리·예측 설명,
구체적 잠정 수련안, 실제 기록을 받아 다음 연구·수련을 조정하는 연결을 확인한다.
이 연결을 지탱하는 기억·문맥·도구 선택·작업 관리·서브에이전트 조정·복구·보고를
함께 설계한다. 하네스 개선은 근거 있는 제안을 제공하는 수준부터 다룬다.

각 기능의 완전한 자동화나 최고 수준 정확도가 첫 버전 조건은 아니다. 하지만 기본
연결에 필요한 기능을 빠뜨리거나, 문서와 도구 목록만으로 동작을 확인했다고 보지 않는다.
선택한 실행 환경에서 지원되지 않는 필수 동작은 대안과 절충을 사용자와 논의한다.

### 장기 확장 또는 미정

| 항목 | 현재 상태 |
| --- | --- |
| 전신 개인 모델 | 현재 문제에 필요한 모델부터 검증하며 확장 |
| 장비·환경·측정 도구 개발 | 비용 여건에 맞춰 단계적으로 실현 |
| 새로운 신체 변화·능력 탐구 | 연구 범위에 포함, 실현 가능성·시점은 미확정 |
| 새로운 무공 체계 창안 | 포함 여부 추후 결정 |
| 실시간 영상·음성 관찰과 코칭 | 첫 버전 필수 여부 미정 |
| PC 종료 중 실행 | 우선 선호, 구현 후보 비교 후 첫 버전 지원 범위 결정 |
| 모바일 세부 작업·플랫폼 | 공식 앱 우선, 실제 범위 추가 확인 |
| 개인 실험·개입 | 허용 범위·평가·중단·추적 조건 개별 구체화 필요 |
| 원본 선별·삭제·정정 | 보존 우선, 권한과 절차 미정 |
| 하네스 변경 적용·평가 절차 | 개선 제안은 포함, 자동 자기 수정은 필수 아님 |

## 6. 기능 연결 확인 시나리오

아래는 기능 설계를 점검할 시나리오다. 테스트를 실행했다는 기록이 아니며 실제 자료와
기준은 검증 단계 전에 구체화한다. 연구 품질과 실행 기능을 별도로 살핀다.

| 장면 | 확인할 결과 |
| --- | --- |
| 목표만 제시하고 초기 기록은 적음 | 필요한 초기 질문과 목표 분석, 미확인을 남긴 전체 설명, 첫 연구 문제와 잠정 수련안 제안 |
| 자료가 많고 서로 다른 결론이 있음 | 폭넓은 조사와 중요한 원문 검토, 독립 근거·재인용 구분, 상충 조건과 후속 질문 도출 |
| 같은 문제를 여러 에이전트가 조사함 | 임무·문맥 전달, 중간 교환, 중복 조정, 근거를 확인한 통합 및 필요한 독립 검토 |
| 도구가 실패하거나 결과가 불충분함 | 실패 원인·영향 확인, 재시도·대체·보류 판단, 미확인을 완료로 보고하지 않음 |
| 관측이 기존 예측과 다름 | 측정·수행 조건 확인, 원인 후보 비교, 모델·수련·다음 질문의 개정 또는 유지 이유 |
| 중단 후 새 세션에서 재개함 | 최신 목표·합의·결과·실제 작업 상태 복원, 완료 작업의 불필요한 반복 방지 |
| 사용자가 방향을 수정하거나 답변을 미룸 | 수정의 영향을 관련 작업에 반영, 미응답 시 기존 합의 범위의 유용한 조사 지속 |
| 하네스의 반복적인 한계가 드러남 | 근거·예상 효과·검증 방법이 있는 개선 제안, 무단 자동 배포 없이 함께 검토 |
| 모바일·구독·외부 자료 조건이 개입함 | 실제 계정 사용량 경로와 지원 동작 확인, 비용·권한·개인 자료 제공 원칙 준수 |

## 7. 아키텍처 설계로 넘길 질문

1. 각 기능을 Codex 기본 기능, 플러그인·스킬·MCP 도구, 프로젝트 코드 중 어디에서 담당할 것인가?
2. 1순위 Codex Cloud에서 사용자 대화·서브에이전트·사용 도구·기억·중단 및 재개가 함께 작동하는가?
3. 메인·서브에이전트가 실제로 어느 계정과 구독 사용량을 쓰며, 호스트의 수명·한도·네트워크 제약은 무엇인가?
4. 연구 원본·개인 자료·장기 기억·작업 상태는 어디에 지속되며, 세션·호스트 변경 시 어떻게 연결할 것인가?
5. 모듈의 책임과 주고받는 정보, 실패·취소·재개 처리와 사용자 제어의 연결은 어떻게 정할 것인가?
6. 실제 연구 성과를 낸 에이전트와 DeepSeek Harness 등 공개 구현에서 무엇을 재사용·이식·변형할 것인가?

기술 참고는 공개 논문·공식 문서·소스 코드와 실제 실행 결과를 구분해 비교한다.
DeepSeek의 플러그인 등록·서비스 연결·루프·수명주기·로그 등 기술을 조사하되
Codex와 동일한 확장 권한·형식이 있다고 가정하지 않는다. 기존 삭제한 설계를 확정안으로 복원하지 않는다.

아키텍처 단계에서는 책임·연결·실행 위치와 핵심 가능성을 결정한다. 정확한 데이터 스키마,
API 인자, 검색 알고리즘, 라이브러리 버전과 세부 구현은 이후 상세 기술 설계로 넘긴다.
