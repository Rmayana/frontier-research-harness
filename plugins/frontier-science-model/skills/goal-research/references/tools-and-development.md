# Tools and development

Read only when choosing specialist tools or changing the research environment.
These are peer capabilities, not required steps, separate services or fixed agents.
Provider examples are discovery hints; inspect live descriptions, matching skills
and current schemas before use. Installation alone does not establish readiness.

| Need | Candidate capabilities | Boundary |
| --- | --- | --- |
| Literature and citations | Existing literature tools; Elicit, Scite, Undermind, Pendar | Inspect original evidence; compare overlapping retrieval when it matters |
| Biological data and observations | Life Science tools, Genomic Intelligence, NGS; local observations | Preserve population, assay, tissue and measurement context |
| Gene manipulation research | Genetic evidence, sequence/function predictions, NGS, relevant BioNeMo tools | Independent tool group; sequence scores do not establish an intervention's effects |
| Drug discovery research | BioNeMo, Boltz, Rowan, Tamarind, property tools, PK-Sim/MoBi | Independent tool group; distinguish structure, dynamics, properties and organism effects |
| Simulation and calculations | Installed engines, Rowan/Tamarind dynamics, Wolfram, temporary code | Match the question and inputs; inference can continue without a simulator |
| Models, data and compute | Hugging Face; specific Proto tools | Check deployment, data permissions and authorized cost before submitting |
| Experimental services | Adaptyv and other services within their actual scope | Preparation is distinct from external submission, payment and real-world action |
| Analysis and presentation | Native code and visuals; relevant Data Analytics skills | Use scientific comparisons; do not import business KPI governance |
| Engineering investigation | GitHub source/issue access, Firecrawl developer search, official docs | Compare original implementations, versions and failure reports |
| Engineering verification | Existing tests, Engineering Guardrails, scoped Plugin Eval checks | Packaging scores are not scientific intelligence or measured efficiency |

Choose the best-fitting available route. Do not call every overlapping provider.
If a route fails or lacks a capability, inspect alternatives before calling it
unavailable. Use native APIs/CLIs directly; introduce an adapter only for repeated,
demonstrated friction. Read-only capability inspection does not authorize paid jobs.

Preserve useful outputs and their source/version in ordinary files or existing
research records. Record what the result changes in current_understanding when
material. There is no provider-specific database or mandatory experiment registry.
Model-limited outputs and chained inferences retain their different meanings.

## Improving the environment while using it

For a non-trivial change, inspect the current implementation and the relevant
maintained upstream code/examples. Compare only candidates that could change the
decision. Explain what to reuse, adapt or reject; inspect license, maintenance,
security and integration cost before adoption. Prefer native capabilities or a
small proven dependency over a second agent runtime.

Useful references: [PaperQA](https://github.com/Future-House/paper-qa) for evidence
tools, [smolagents](https://github.com/huggingface/smolagents) for minimal code/tool
composition, and [AstaBench](https://github.com/allenai/asta-bench) for research
behavior evaluation. Recheck current fit; these are not dependencies or a required
reading list. Asta Paper Finder's public snapshot describes itself as unmaintained.

Use observed friction, missed capabilities, repeated work and unnecessary context
to choose small improvements. Preserve the approved goal and useful records;
remove code only after checking its callers and compatibility obligations. Keep
scientific evaluation outside the research loop: no automatic research score or gate.
When reporting substantial work, briefly name plugins actually used, what they
contributed and material limits; distinguish reading a skill from executing a tool.
